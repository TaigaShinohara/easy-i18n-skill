# らくに多言語対応

## 概要（発動条件と結論）

- アプリやサイトを多言語対応したいときに使う。「多言語対応して」「英語対応して」「翻訳を追加して」「i18n」「ローカライズ」で発動する。

- 結論を先に固定する。最もらくで効果的で効率がよい方法は、正本を1つだけにすることである。意味キーと ICU MessageFormat で書いた中央カタログ `messages/en.json` を正本とし、他の言語はそこからだけ翻訳し、各プラットフォームは標準ランタイムで生成物だけを使う。

- 単一プラットフォームだけのプロジェクトでは中央カタログを無理に作らない。そのプラットフォームの標準ファイル自体を正本にする。Android 単体なら `res/values/strings.xml`、Web 単体ならその Web の JSON が正本である。

- このスキルの成果物は3つである。対象プロジェクトに合った方式の判定、実際に動くカタログと配線、未訳とプレースホルダ崩れを検出する検証結果である。

## 絶対のルール

- ハードコードされた表示文字列を残さない。ボタン、見出し、エラー、空状態、通知、アクセシビリティラベルまで全てカタログ経由にする。後から国際化するコストは最初からやるコストよりはるかに高い。

- 文字列を連結して文を作らない。語順は言語で変わる。変数を含む文は必ず1つの完全なメッセージにし、翻訳者がプレースホルダの順序を入れ替えられる形にする。

- 複数形と性別と順序数をコードの分岐で書かない。`count == 1` のような判定は英語でしか正しくない。ICU の `plural` と `select` と `selectordinal` に寄せ、言語ごとの形は翻訳側に持たせる。詳細は [ICUチートシート](references/icu-cheatsheet.md) を使う。

- 日付と数値と金額と並び順を手で整形しない。Web では `Intl.DateTimeFormat` と `Intl.NumberFormat` と `Intl.Collator` を使い、Android では `android.icu` 系とロケールを明示した整形を使う。保存は UTC と ISO 形式と通貨コードで行う。

- 生成ファイルを手で編集しない。Android の `strings.xml` や Chrome 拡張の `_locales` を中央カタログから生成する場合は、直す場所は常に中央カタログである。生成物だけを直すと次回生成で消える。

- 翻訳でプレースホルダとタグと改行を壊さない。`{name}` や `%1$s` や HTML タグは一字も変えずに残すよう翻訳指示に明記し、検証スクリプトで機械的に確認する。

- MessageFormat 2 を既定にしない。2026年時点では対応ライブラリが少なく移行先が安定していないため、既定は ICU MessageFormat の第1世代である。将来の置き換えはライブラリ側で吸収できる形にしておく。

- 有料の翻訳管理サービスを既定にしない。個人開発では Git と CLI で足りる。2人目の人間の翻訳者が加わったときに初めて Crowdin の無料枠などを検討する。

## 方式を決める

- [方式の判断表](references/decision-matrix.md) で対象を判定する。判定の軸は、プラットフォームの数、フレームワーク、既存カタログの有無、人間の翻訳者がいるかどうかである。

- 判定の既定は次のとおりである。
  - Next.js の App Router なら `next-intl` を使う。ICU が内蔵されサーバーコンポーネントと相性がよい。
  - Vite と React の新規プロジェクトなら Paraglide JS を使う。コンパイラ方式で型安全な関数が生成され実行時が小さい。
  - 共有コードが多い場合や最大のエコシステムが要る場合は `react-i18next` と `i18next-cli` を使う。
  - 人間の翻訳者と PO ファイルで回す場合は Lingui を使う。
  - Android 単体なら標準リソースだけを使う。サードパーティ製の文字列ライブラリは既定では入れない。
  - iOS と macOS のネイティブアプリなら String Catalogs を使う。中央カタログがある場合はそこから生成し、単体ならカタログ自体を正本にする。
  - Chrome 拡張なら `chrome.i18n` を必ず使う。マニフェストの名前と説明はこれでしか翻訳できない。
  - Kotlin Multiplatform で UI まで共有する場合だけ Compose Multiplatform のリソースを使う。

- 既存プロジェクトに別の方式が既に入っている場合は、動いている方式を尊重する。全面移行は翻訳資産と検証が揃う場合だけ提案し、理由と移行手順を添える。

## カタログを作る

- 正本の置き場所を固定する。複数プラットフォームならリポジトリ直下の `messages/` に置く。単体ならそのプラットフォーム標準の場所に置く。

- キーは意味キーにする。階層は `機能.要素_役割` の形にし、英語の文をキーにしない。文言変更でキーが壊れず、同じ英語でも意味が違う場合に衝突しないためである。良い例は `cart.checkout_cta` で、悪い例はキー自体が英語文の場合と `common.text1` のような意味のない連番である。

- 変数を含む文字列は ICU で書く。単純な文字列はそのままの文でよい。ICU が必要なのは複数形と性別と順序数と埋め込みの数値や日付がある場合である。

- 曖昧なキーには文脈メモを必ず付ける。たとえば `Open` は動詞か形容詞かで訳が変わる。Chrome 形式では `description` 欄を使い、Web の JSON では用語集やカタログ横のメモで文脈を残す。

- 用語集を最初に作る。固有名詞の訳さない語、製品用語の確定訳、敬語や一人称などの文体方針を [用語集テンプレート](templates/glossary.md) で残す。翻訳の品質はモデルよりも用語集と文脈で決まる。

- フォールバックを決める。完全なロケール、言語のみ、既定言語の順に探し、既定言語には全キーを必ず揃える。キーが見つからない場合に生のキーを画面に出さない。

## 翻訳する

- [翻訳ワークフロー](references/translation-workflow.md) に従う。要点は差分だけ翻訳することである。全量を毎回翻訳し直すとコストも崩れも増える。

- 既定の翻訳手段は、自分の LLM キーを使える差分翻訳 CLI である。第一候補は Lingo.dev の CLI で、ロックファイルで変わった文だけを処理できる。導入できない環境では DeepL や Google 翻訳の無料枠、または同梱方式の自作スクリプトで差分だけを翻訳する。どの道具でも差分だけを対象にする原則は変えない。

- 翻訳指示には次の4点を毎回含める。プレースホルダとタグを壊さないこと、用語集に従うこと、UI 向けに短く保つこと、文脈メモを尊重することである。

- 人の確認は全量にかけない。大事な約20文だけを確認する。対象はオンボーディング、課金画面、エラー、ストア掲載文である。残りは機械翻訳のドラフトとして印を残し、後から直せる状態にする。

- 法務と医療と課金の文言は機械翻訳のまま公開しない。その範囲だけは人の確認を必須にする。

## プラットフォームへ配る

- [プラットフォーム別ガイド](references/platform-guides.md) の該当節だけを読む。全プラットフォーム分を毎回読まない。

- 中央カタログから生成する場合は同梱の変換スクリプトを使う。`scripts/convert_catalog.py` は中央 JSON から Android の `strings.xml` と Chrome 拡張の `_locales` を作る。変換で最も壊れやすいのは複数形とプレースホルダなので、変換後は必ず検証する。

- Android ではアプリ別言語設定を有効にする。生成されたロケール一覧と `AppCompatDelegate.setApplicationLocales()` の経路を確認する。

- Chrome 拡張ではマニフェストに `default_locale` を入れ、名前と説明に `__MSG_` 参照を使う。詳細説明とスクリーンショットはストア側で言語別に入力する別物であることを忘れない。

- Web ではロケールを URL に含め、`lang` 属性と `hreflang` を付ける。Cookie だけの切り替えは検索エンジンに見えない。

## 検証する

- 同梱スクリプトで機械検証する。`scripts/validate_locales.py` は全ロケールでキー集合が一致すること、プレースホルダ集合が一致すること、空訳がないことを確認する。1件でも失敗したら公開しない。

- 擬似ロケールで先に試す。`scripts/pseudo_localize.py` で母音にアクセントを付け長さを3割から4割増やした偽翻訳を作り、ハードコード残りとレイアウト崩れと文字化けを実翻訳の前に潰す。

- プラットフォーム標準の検査も回す。Web は採用ライブラリの CLI の厳格モード、Android は Lint の MissingTranslation と HardcodedText を使う。

- 目視確認は決めた観点だけで行う。最も長い言語での切れ、RTL を名乗る場合の実 RTL、複数形は 0 と 1 と 2 と 5 と 21 と 100、日付と金額の各ロケール表示、言語切り替えの保持、キーを1つ消したときのフォールバック表示である。詳細は [落とし穴と確認リスト](references/pitfalls-and-qa.md) を使う。

- 対応率が9割に届いたら公開してよい。キー単位のフォールバックがあるプラットフォームでは部分訳でも安全に公開できる。生キーが画面に出る状態では公開しない。

## ストア掲載文を扱う

- [ストア掲載文の扱い](references/store-listing.md) に従い、アプリ内翻訳とは完全に別作業として扱う。アプリを翻訳しても掲載文は自動では翻訳されない。

- 掲載文の優先順位は固定する。タイトル、短い説明、スクリーンショットの順に先に訳し、長い説明は最後にする。

- 掲載文の正本は `store/<locale>/listing.md` に置き、[掲載文テンプレート](templates/store/listing.md) を使う。ストア画面へはそこから貼ることでずれを防ぐ。

## Alternatives for better results

- 既に翻訳管理サービスを使っているプロジェクトでは、そのサービスの書き出しを正本の隣に置き、このスキルの検証だけを流用すると移行コストなしに崩れ検出が得られる。

- 言語数を増やす前に国別の利用データを見る。2言語を丁寧に訳す方が8言語の粗い訳より効果が高い。

- ストアに出す段階では store_review_readiness と store_listing_pack のスキルと組み合わせ、掲載文の翻訳を素材パックの必須項目に入れる。
