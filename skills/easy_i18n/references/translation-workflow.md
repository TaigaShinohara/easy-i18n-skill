# 翻訳ワークフロー

## 流れ

- 手順は固定する。正本を更新する、差分だけを翻訳する、機械検証する、大事な文だけ人が見る、コードと一緒にコミットする、の順である。

- 翻訳対象は常に正本との差分だけにする。変わっていない文を再翻訳すると訳が揺れ、コストもかかる。差分管理はロックファイルやハッシュで変わった文だけを拾う道具に任せる。

- 道具の第一候補は Lingo.dev の CLI である。自分の LLM キーを使い、変わった文だけを処理し、用語集も渡せる。使えない環境では DeepL や Google 翻訳の無料枠を差分にだけ当て、さらに軽い方法として検証スクリプトと組み合わせた自作の差分翻訳スクリプトでもよい。道具が変わっても、差分だけ、用語集を渡す、検証を通す、の3点は変えない。

## 費用の目安

- 2026年時点の目安として、典型的な個人アプリの300から800キー、約3万文字なら、無料枠か安い LLM で1言語あたり0から5ドル程度に収まる。道具代は Git と CLI だけなら月額ゼロである。

- 機械翻訳 API は文字数課金で、無料枠があるサービスも多い。LLM はトークン課金で、安い小型モデルが UI 文の大量翻訳では最も割がよい。価格は変わるため実行前に公式の料金を確認する。

- 人間の翻訳は単語単価と日数がかかる。個人開発では掲載文と課金まわりだけに絞って使う。

## 翻訳指示に入れるもの

- プレースホルダと HTML タグと改行を一字も変えないこと。

- 用語集の確定訳と訳さない語に従うこと。

- UI の文として短く保つこと。特にボタンと見出しは元の長さを超えにくくすること。

- 文脈メモがある場合はその場面に合う訳にすること。品詞が曖昧な短い文ほど文脈が重要である。

- 文体方針に従うこと。ドイツ語の敬称、スペイン語の敬称、日本語の丁寧さなど、用語集に決めを書いておく。

## 人の確認の絞り方

- 全文を確認しない。確認するのは売りと信頼に直結する約20文である。具体的には最初の画面、課金画面、主要なエラー、ストア掲載文である。

- 確認者は母語話者が理想だが、最初の公開では知人の確認や少額の外注スポットチェックでも十分な前進になる。

- 機械翻訳のままの文には印を残す。後から優先順位を付けて直せるようにするためである。印がないとどれが確認済みか分からなくなる。

## 用語集の育て方

- 用語集は翻訳のたびに育てる。訳が揺れた語、訳してはいけない固有名詞、ブランドの言い回しが出たらその場で足す。

- 用語集はリポジトリに置き、カタログと同じコミットで更新する。翻訳道具が読める場所に置くことが重要である。
