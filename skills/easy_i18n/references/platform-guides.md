# プラットフォーム別ガイド

対象の節だけを読む。

## Next.js

- ライブラリは next-intl を使う。カタログは中央 JSON をそのまま読み込める。

- ロケールは URL に含める。ミドルウェアとナビゲーションはライブラリの提供するものを使い、自前で Cookie だけに寄せない。

- サーバーコンポーネントではサーバー側の取得関数を使い、クライアント側のフックと混ぜない。

- 型安全はメッセージの型宣言を有効にして得る。キーの打ち間違いをコンパイルで止めることが目的である。

## Vite と React

- 新規では Paraglide JS を使う。カタログから型安全な関数が生成されるため、呼び出しは関数の形になる。生成フォルダは手で編集しない。

- react-i18next を使う場合は新しい CLI である i18next-cli で抽出と同期と型生成を行う。旧来のパーサーは使わない。

- どちらの場合も検証は厳格モードを CI に入れる。未訳や未使用キーがあればビルドを止める。

## Android

- 置き場所は `res/values/strings.xml` を既定言語とし、言語ごとに `values-es` や `values-de` のようなフォルダを作る。既定フォルダには全キーを必ず入れる。欠けるとその言語の利用者で問題になる。

- Compose では `stringResource()` で文字列を、`pluralStringResource()` で複数形を読む。どちらもロケール変更で再構成される。

- ViewModel の中で文字列を取得しない。Context が要る取得は UI 側で行い、ViewModel からはリソース ID と引数を渡す。

- 変数は位置指定のプレースホルダで受ける。例は `%1$s` と `%1$d` である。文の連結は Lint でも警告されるため行わない。

- アプリ別言語設定を使う。新しいビルド設定ではロケール一覧が自動生成される。古い構成では `locales_config.xml` を用意し、`AppCompatDelegate.setApplicationLocales()` で切り替える。

- RTL が要る場合はマニフェストで RTL 対応を宣言し、余白は Start と End の論理方向で指定する。

- 検証は Lint の MissingTranslation と HardcodedText を使う。擬似ロケールはビルド設定で有効化でき、アクセント付きと擬似 RTL が開発者向け設定に出る。

## Chrome 拡張

- 置き場所は `_locales/<locale>/messages.json` である。各キーは `message` と文脈用の `description` と必要なら `placeholders` を持つ。

- マニフェストには `default_locale` を必ず入れる。`_locales` があるのに既定ロケールがないと読み込めない。

- マニフェストと CSS では `__MSG_key__` の形で参照し、JavaScript では `chrome.i18n.getMessage()` で取得する。

- フォールバックはキー単位である。完全なロケール、言語のみ、既定ロケールの順に探すため、訳が途中までの言語でも安全に出せる。

- 複数形は標準では提供されない。`Intl.PluralRules` でカテゴリを選びキーを使い分けるか、複数形が多い画面では ICU の整形ライブラリを埋め込む。

- ストアの長い説明とスクリーンショットはパッケージからは読まれない。ダッシュボードで言語別に入力する。詳細は store-listing の参照を使う。

## 静的サイトと一般の Web

- ページ本文はアプリと同じカタログで扱う。タイトルと説明文と Open Graph は専用の `meta` 系キーに分けて忘れないようにする。

- `html` の `lang` 属性と `hreflang` とロケール別サイトマップを揃える。言語切り替えを Cookie だけにすると検索結果に現れない。
